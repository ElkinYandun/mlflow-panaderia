Dataset

El proyecto de ejemplo

El archivo data/bakery_sales_dataset.csv contiene 19.321 líneas de venta y 40 columnas. Cada fila describe un producto vendido en una tienda: categoría, precio, cantidad, clima, temporada, promoción, almacenamiento y el resultado de la venta. La variable que se quiere anticipar es el desperdicio.

DatoValor
Archivodata/bakery_sales_dataset.csv (UTF-8 con BOM)
Filas y columnas19.321 × 40
Variable objetivoAlto_Desperdicio = 1 si Waste_Pct > 33.3; si no, 0
DistribuciónClase 0: 12.833 (66,42 %) · Clase 1: 6.488 (33,58 %)
Columnas de entrada29 después de excluir identificadores, fecha/hora y resultados posteriores a la venta
Partición80 % entrenamiento (15.456 filas) y 20 % prueba (3.865 filas), estratificada

El objetivo se construye en src/data.py a partir de Waste_Pct, que es el porcentaje de producto no vendido. El umbral de 33,3 % separa un tercio de desperdicio: por encima se considera alto.

Por qué se excluyen columnas

Un modelo útil tiene que decidir antes de que ocurra la venta. Si se le pasan Units_Sold, Unsold_Units o Profit, aprende a copiar el resultado y en producción no tendría esos datos. Eso se llama fuga de información (leakage) y produce métricas espectaculares que no sirven.

Columna excluidaMotivo
Order_ID, Customer_IDIdentificadores; no generalizan a pedidos nuevos
Date, TimeSe usan Year, Month, Day y Hour; la fecha exacta no aporta y puede filtrar tendencias
Waste_PctEs el origen de la variable objetivo: incluirla sería copiar la respuesta
Unsold_Units, Stock_Available, Units_Produced, Units_SoldResultados que solo se conocen después de la venta
ProfitSe calcula con las unidades vendidas y los costos reales
Customer_RatingSe registra después del consumo y en este dataset resultó casi aleatoria (accuracy ≈ 0,464, igual que la clase mayoritaria)
Alto_DesperdicioEs la etiqueta; nunca entra como variable de entrada

Las 29 columnas que sí entran se dividen en categóricas y numéricas en src/config.py. El pipeline imputa nulos, aplica one-hot a las categóricas y entrena un bosque aleatorio. Así el modelo solo usa información disponible al planificar la producción.

RunConfiguraciónaccuracyf1_macro

Resultado esperado
Un experimento desperdicio-panaderia con tres runs, el modelo clasificador-desperdicio en versión 1 con los alias champion y challenger, y un archivo predicciones.csv con 22 ceros y 28 unos.
Por qué importa el umbral
La clase positiva es el 33,58 % de los datos, así que un modelo que siempre diga «no hay desperdicio alto» acertaría el 66,42 %. Por eso se miran también f1_macro, recall y ROC-AUC: el accuracy solo no demuestra que el modelo sea útil.

Organizar el proyecto

Una estructura simple y estable hace que cualquier compañero encuentre qué ejecutar y qué guardar en Git.

Estructura

Estructura recomendada

Por qué
El notebook sirve para explorar. El código que se repite (cargar datos, entrenar, registrar) vive en src/ como scripts que se ejecutan desde la terminal, desde mlflow run o desde un pipeline, sin abrir Jupyter. Separar config, data y train permite cambiar una pieza sin tocar las demás.
Consejo
Una base de datos y una carpeta de archivos por proyecto. Si varios proyectos comparten el mismo mlflow.db, sepáralos con experimentos distintos.
Código

El código base del proyecto

Estos archivos se ejecutaron tal como aparecen. Cópialos a src/ y a la raíz del proyecto.

Por qué
config.py concentra los nombres y las listas de columnas para que no haya dos versiones distintas del mismo dato. train.py recibe sus parámetros por línea de comandos (argparse), lo que permite probar configuraciones sin editar código. Guarda model_uri como etiqueta del run, y así register.py encuentra el modelo sin adivinar rutas.
Atención
train.py solo llama a mlflow.set_experiment() cuando no lo ejecuta mlflow run. Si lo llamaras siempre, mlflow run fallaría con «active experiment ID does not match environment run ID».
Atención
El CSV tiene BOM. Sin encoding="utf-8-sig", la primera columna se llama \ufeffOrder_ID y las listas de columnas de config.py no coinciden. El mismo cuidado se aplica al leer nuevos_pedidos.csv en predict.py.
Consejo
skops_trusted_types incluye sklearn.tree._tree.Tree y numpy.dtype. Son los tipos que MLflow 3.18 necesita autorizar para serializar el Pipeline. Declara solo tipos de modelos que entrenaste tú.
Convención

Convenciones de nombres

ElementoCómo nombrarloEjemplo

Por qué
Comparar runs exige que los nombres coincidan. Si un intento guarda acc y otro accuracy, la interfaz los muestra como métricas distintas y no se pueden ordenar juntos.
Terminal

Entorno virtual y archivos de apoyo

Por qué
requirements.txt junto con el código es lo que permite reproducir el experimento en otra máquina. Las variables de entorno mantienen fuera del código cualquier dato que cambie según dónde se ejecute: direcciones, usuarios, claves.
Atención
En esta guía mlflow run se ejecuta con el entorno virtual activado. MLflow llama a python y, si el venv no está activo, el comando falla con bash: línea 1: python: orden no encontrada. Activa siempre .venv antes de usar mlflow run.
Parte B

Configurar y ejecutar

Decidir dónde se guardan los datos, abrir la interfaz y ejecutar el código de las distintas formas posibles.

Concepto

A dónde guarda MLflow

Importar mlflow no guarda nada. Los datos se guardan cuando el código ejecuta una función log_*, y el lugar lo decide el tracking URI. MLflow separa dos tipos de información:

InformaciónEjemplosDónde queda
MetadatosParámetros, métricas, etiquetas, versiones del registroBase de datos: mlflow.db
ArchivosModelos, gráficos, CSVCarpeta mlruns/

Hay tres formas habituales de configurarlo:

OpciónMLFLOW_TRACKING_URICuándo usarla
Archivo localsqlite:///mlflow.dbAprender y trabajar solo. No necesita servidor encendido.
Servidor localhttp://127.0.0.1:5000El notebook y los scripts envían los datos a un servidor que tú encendiste.
Servidor del equipohttp://servidor:5000Equipo o producción, con PostgreSQL y un almacén de objetos detrás.
Atención
Si no configuras nada, MLflow 3.18 crea mlflow.db en la carpeta desde la que ejecutas el código. Dos carpetas distintas son dos historiales distintos, y esa es la causa más común de una interfaz vacía.
Atención
La base de datos guarda las rutas de los archivos como rutas absolutas. Si mueves o renombras la carpeta del proyecto, los modelos registrados dejan de cargar con el error No such artifact. Para compartir un modelo, guárdalo en una carpeta propia (sección Guardarlo en una carpeta) o usa un servidor.
Por qué
Separar metadatos de archivos es lo que permite, más adelante, pasar de SQLite a PostgreSQL y de una carpeta a un bucket S3 sin cambiar el código de entrenamiento.
Terminal

Abrir la interfaz

Por qué
mlflow ui y mlflow server arrancan el mismo servidor. Indicar --backend-store-uri de forma explícita evita abrir por accidente un almacén distinto del que usó tu código. La interfaz solo muestra lo que ya está guardado: puedes apagarla y encenderla sin perder datos.
Consejo
Si ves el error Address already in use, hay otra interfaz abierta en ese puerto. Cierra la anterior o elige otro puerto con --port. En este proyecto la interfaz se verificó en el puerto 5000 y el servicio del modelo en el 5001.

Código

Parámetros

Por qué
Un parámetro es una entrada que decides tú antes de entrenar. Guardarlo es lo que permite responder más tarde «¿con qué configuración salió este resultado?».
Consejo
Registra también la semilla y el tamaño de la partición. Sin ellos, los resultados no se pueden reproducir. En este proyecto la semilla es 42 y la partición 80/20 estratificada.
Código

Métricas

Por qué
Las métricas se guardan como números. Con step la interfaz dibuja una curva, útil para pérdida o accuracy por época.
Atención
Si una métrica nunca se guardó, la columna metrics.nombre no existe en search_runs y pandas lanza KeyError. En este proyecto todos los runs de entrenamiento guardan accuracy y f1_macro, pero el run de evaluación usa nombres distintos, como accuracy_score, f1_score y roc_auc.
Código

Etiquetas

Por qué
Las etiquetas no son resultados ni configuración: sirven para organizar y filtrar (quién lo hizo, con qué datos, en qué etapa). La etiqueta especial mlflow.note.content aparece como descripción del run en la interfaz.
Código

Artefactos: archivos, gráficos y tablas

Por qué
Un artefacto es cualquier archivo ligado al run. Guardar la matriz de confusión o una muestra de datos junto a las métricas deja la evidencia en el mismo lugar. log_text, log_dict y log_figure ahorran crear archivos temporales.
Consejo
Si el script se ejecuta sin pantalla (servidor, CI), usa matplotlib.use("Agg") antes de importar pyplot. En este proyecto train.py ya lo hace.
Atención
Los artefactos pesados (cientos de MB) ralentizan la interfaz y llenan el disco. Guarda muestras o resúmenes, no los datos completos. Por eso el proyecto guarda muestra_predicciones.csv con 25 filas y no las 3.865 filas de prueba.
Código

Registrar el dataset

Por qué
Registrar el dataset deja constancia de qué datos usó cada run, con una huella (hash) que cambia si los datos cambian. Es la respuesta a «¿este modelo se entrenó con la versión vieja o con la nueva?».
Consejo
Registra también el conjunto de prueba con context="testing" si quieres dejar trazabilidad completa de la evaluación.
Código

Guardar un modelo

Dentro de la carpeta del modelo quedan estos archivos:

ArchivoContenido
MLmodelDescripción del modelo: tipo, firma de entrada y salida
model.skopsEl pipeline serializado de scikit-learn
requirements.txtLas librerías con las versiones exactas del entrenamiento
python_env.yaml y conda.yamlLa versión de Python y el entorno para reconstruirlo
input_example.json y serving_input_example.jsonUn ejemplo de entrada, listo para probar la API
Por qué
La firma (signature) es el contrato del modelo: si alguien envía columnas distintas, la API responde 400 en vez de predecir con datos erróneos. requirements.txt permite reconstruir el entorno exacto cuando se empaqueta el modelo.
Atención
MLflow guarda los modelos de scikit-learn con skops y exige declarar los tipos confiables con skops_trusted_types. En este proyecto el Pipeline necesita sklearn.tree._tree.Tree y numpy.dtype. Declara solo los de modelos que entrenaste tú: es la protección contra archivos de modelo maliciosos. Para otras librerías usa su propio sabor: mlflow.xgboost, mlflow.pytorch, mlflow.tensorflow.
Código

Registro automático

Por qué
autolog sirve para empezar rápido o probar una librería nueva. Para trabajo que llega a producción conviene el registro explícito: sabes exactamente qué quedó guardado y con qué nombres, y los runs de todo el equipo son comparables.
Atención
Con un Pipeline que incluye OneHotEncoder, el autolog de MLflow 3.18 registra el modelo y las métricas, pero puede generar avisos sobre la firma. En este proyecto se verificó que entrena y registra correctamente; aun así, el código de train.py usa registro explícito para controlar la firma y el ejemplo de entrada.
Código

Runs anidados

Por qué
Una búsqueda de hiperparámetros genera muchos intentos. Un run padre con hijos los agrupa en la interfaz como un solo bloque desplegable, en vez de decenas de filas sueltas.
Código

Modelo con lógica propia (pyfunc)

Por qué
Con PythonModel empaquetas cualquier lógica: preprocesamiento, reglas de negocio, varios modelos juntos. El resultado se carga y se sirve igual que cualquier otro modelo de MLflow.
Atención
MLflow avisa de que el objeto se serializa con CloudPickle. Es normal, pero un modelo así puede ejecutar código al cargarse: carga solo modelos propios o revisados.
Código

Evaluar un modelo guardado

Por qué
mlflow.models.evaluate calcula un conjunto estándar de métricas y las guarda en el run. Se puede usar como criterio de aceptación antes de promover un modelo. En este proyecto produjo roc_auc=0.9390, f1_score=0.8541 y log_loss=0.2701.
Atención
Con MLflow 3.18, pandas 3.1 y shap instalado, mlflow.models.evaluate puede fallar con TypeError: Cannot interpret '<StringDtype(na_value=nan)>' as a data type. La solución que usa src/evaluate.py es evaluator_config={"log_model_explainability": False}: las métricas se calculan igual y no se generan explicaciones SHAP.
Consejo
El aviso «model type looks like None» es informativo; las métricas se calculan correctamente. Si quieres explicaciones, exporta los datos a tipos NumPy antes de llamar a evaluate o desactiva SHAP como en este proyecto.
Código

Guardarlo en una carpeta propia

Por qué
Una carpeta de modelo es autocontenida: incluye el modelo, la firma y las dependencias, y se puede mover o copiar a otra máquina sin depender de la base de datos. Es la forma de compartir un modelo con un compañero y la entrada de mlflow models serve y de Docker.
Consejo
Para obtener esa misma carpeta desde un modelo ya registrado, usa mlflow artifacts download --artifact-uri "models:/clasificador-desperdicio@champion" --dst-path model.
Parte D

Consultar y cargar

Encontrar los runs que interesan, traer sus archivos y usar los modelos guardados.

Código

Buscar y comparar runs

La cadena de filter_string usa esta sintaxis:

Qué filtrasEjemplo
Una métricametrics.accuracy > 0.88
Un parámetro (siempre como texto)params.max_depth = '8'
Una etiquetatags.etapa = 'desarrollo'
El nombre del runtags.mlflow.runName = 'rf_n200_d12'
El estadoattributes.status = 'FINISHED'
Varias condicionesmetrics.f1_macro > 0.88 AND params.seed = '42'
Por qué
search_runs devuelve una tabla de pandas, así que puedes ordenar, filtrar y graficar con las herramientas que ya conoces. El cliente (MlflowClient) da acceso a un run concreto: su historial de métricas y sus archivos.
Atención
Los parámetros se guardan siempre como texto. Por eso se comparan con comillas: params.max_depth = '8', no = 8.
Consejo
Para comparar solo runs de entrenamiento, filtra tags.mlflow.runName != 'evaluacion-champion' o usa la etiqueta tags.etapa = 'desarrollo'. El run de evaluación guarda otras métricas, como accuracy_score, f1_score y roc_auc.
Código

Descargar artefactos desde código

Por qué
Sirve para traer un gráfico, una muestra de datos o cualquier archivo de un run antiguo sin abrir la interfaz. En este proyecto el artefacto está en datos/muestra_predicciones.csv porque train.py lo registra con artifact_path="datos".
Código

Cargar un modelo

Por qué
pyfunc.load_model funciona con cualquier modelo de MLflow y siempre expone predict. El sabor específico (mlflow.sklearn.load_model) devuelve el objeto original y da acceso a sus métodos propios. En este proyecto el objeto es un Pipeline, así que predict_proba funciona sobre el pipeline completo.
Consejo
Antes de enviar datos a un modelo, mira get_input_schema(): te dice qué columnas y tipos espera. La API también valida esa firma y responde 400 si falta una columna.
Parte E

Model Registry

Dar nombre y versión a los modelos candidatos, promoverlos y volver atrás sin reentrenar.

Código

Registrar, promover y volver atrás

Quiero...Hago...
Crear una versión nuevamlflow.register_model(uri, nombre)
Marcar un candidatoset_registered_model_alias(nombre, "challenger", version)
Promover a producciónset_registered_model_alias(nombre, "champion", version)
Volver a la versión anterior (rollback)set_registered_model_alias(nombre, "champion", version_anterior)
Saber qué versión es championget_model_version_by_alias(nombre, "champion")
Ver todos los alias de un modeloget_registered_model(nombre).aliases
Por qué
Sin registro, «el modelo de producción» es un archivo suelto que nadie sabe de dónde salió. Con alias, el código de producción pide models:/nombre@champion y no necesita conocer el número de versión: promover o revertir se reduce a mover una etiqueta.
Atención
search_model_versions no incluye los alias en su resultado. Para verlos usa get_registered_model(nombre).aliases o get_model_version(nombre, version).aliases.
Consejo
El registro también se ve y se edita en la pestaña Models de la interfaz. En este proyecto los alias quedaron como {'challenger': 1, 'champion': 1}.
Parte F

Servir y empaquetar

Publicar el modelo como una API REST, predecir desde la terminal y preparar la base de una imagen Docker.

Terminal

Con el servicio activo, en otra terminal:

Por qué
Un endpoint HTTP permite que cualquier lenguaje o sistema use el modelo sin instalar Python. /ping y /health son los que Docker y Kubernetes consultan para saber si el servicio puede recibir tráfico.
Atención
El servidor de MLflow no autentica las peticiones. No lo expongas a Internet sin un API gateway o una red privada delante.
Probado
En este proyecto el servicio respondió 200 en /ping y /health, devolvió 3.18.0 en /version, predijo con CSV y JSON, y respondió HTTP 400 cuando se omitieron columnas obligatorias.
Terminal

Predecir desde la terminal

Por qué
Es la forma más corta de probar un modelo con datos nuevos, y sirve para trabajos por lotes (por ejemplo, puntuar un archivo cada noche).
Consejo
En línea (models serve) cuando alguien espera la respuesta en milisegundos. Por lotes (models predict o un script) cuando se procesan muchos registros y la latencia no importa.

Preparar la imagen Docker

Consejo
Para producción conviene escribir tu propio Dockerfile con usuario sin privilegios, chequeo de salud y etiquetas por versión. La imagen generada es un punto de partida, no el producto final.
Parte G

Administración desde la terminal

Listar, inspeccionar, exportar y limpiar experimentos sin abrir la interfaz.

Terminal

Experimentos, runs y artefactos

Todos estos comandos usan MLFLOW_TRACKING_URI para saber a qué almacén conectarse.

Atención
La opción -v (--view) solo acepta active_only (por defecto), deleted_only y all. Con cualquier otro valor, por ejemplo deleted, el comando falla con un error largo.
Por qué
Los comandos de terminal sirven para automatizar tareas (exportar resultados, limpiar runs viejos) y para trabajar en servidores sin interfaz gráfica. El id del experimento se ve con experiments search, y el del run con runs list.
Consejo
En este proyecto el experimento desperdicio-panaderia tiene id 1. Los comandos experiments csv y runs list se verificaron con ese id.
Terminal

Borrar y limpiar

Borrar en MLflow tiene dos niveles. El primero se puede deshacer.

Por qué
Primero delete y después, con calma, gc. gc elimina para siempre los metadatos y los archivos de los runs que estaban en la papelera.
Atención
gc no tiene vuelta atrás. Revisa con runs list -v deleted_only qué hay en la papelera antes de ejecutarlo. Si el servidor guarda los archivos por HTTP, define MLFLOW_TRACKING_URI antes de usar gc.

Lista

Hábitos que evitan problemas

  • Fijo MLFLOW_TRACKING_URI antes de ejecutar nada y compruebo con get_tracking_uri().
  • Guardo parámetros, semilla, métricas, firma y ejemplo de entrada en cada run.
  • Uso nombres de runs descriptivos y las mismas claves de parámetros y métricas en todos los intentos.
  • Excluyo del modelo toda columna que solo se conoce después de la venta.
  • Cargo los modelos por alias, nunca por un número de versión escrito en el código.
  • No muevo ni renombro la carpeta de un proyecto con experimentos. Para compartir un modelo uso una carpeta propia o un servidor.
  • Antes de gc reviso qué hay en la papelera.
  • Subo a Git el código y requirements.txt, nunca mlflow.db, mlruns/ ni .env.
Regla de oro
Si el modelo no puede saber un dato en el momento de decidir, ese dato no puede ser una variable de entrada. En esta panadería, Units_Sold, Unsold_Units, Profit y Waste_Pct quedan fuera por esa razón.
